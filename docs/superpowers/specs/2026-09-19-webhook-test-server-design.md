# Whim Webhook Test Server Design

**Date:** 2026-09-19

**Status:** Approved in conversation; awaiting written-spec review

## Purpose

Whim's developers need a disposable local webhook destination for manually testing the app. After Whim delivers Notes, a browser should show what arrived and allow each audio file to be played. This is development tooling, not a Whim-operated backend or a production data store.

## Scope

Extend the existing dependency-free Node webhook fixture rather than introduce a second receiver. The server will continue to validate Whim's v1 multipart contract and support the routes used by automated delivery tests.

The test server will:

- accept Whim webhook requests at the existing receiver routes;
- retain parsed metadata and audio bytes in memory for the lifetime of the process;
- render received Attempts newest-first in a browser;
- show the Note title, creation time, source, duration, event, Note ID, Attempt ID, and duplicate status;
- provide an HTML audio player for each received Attempt;
- clear all received data through the existing reset route; and
- start through a root package script on a predictable local port, overridable by environment variable.

It will not persist files, provide accounts, accept remote traffic by default, transcribe audio, edit Notes, or become part of the shipped iPhone or Watch applications.

## Architecture

`packages/WhimCore/Sources/WhimCore/WebhookConfiguration/Fixtures/webhook-server.mjs` remains the single executable server. Its existing request verification produces a received-Attempt record containing parsed metadata, identity fields, duplicate status, and the exact audio bytes.

The server binds to `127.0.0.1` by default. `WHIM_WEBHOOK_HOST` overrides the bind address; `0.0.0.0` enables access through all IPv4 interfaces. An unset or empty host retains the loopback default. A root `npm` script starts it with a stable development port while `WHIM_WEBHOOK_PORT` continues to override that port, including the current port-zero behavior used by automated tests.

No runtime dependencies are added. HTML and CSS are generated by the fixture, and browser behavior uses a small inline script if periodic refresh is needed.

## HTTP Interface

- `POST /receive` and the existing response-simulation paths continue accepting and acknowledging valid Whim multipart requests.
- `GET /` returns the inspection page. It renders an empty state until a request arrives and then lists received Attempts newest-first.
- `GET /audio/<attempt-id>` returns the retained audio bytes with the `audio/mp4` media type. Unknown IDs return `404`.
- `GET /state`, `POST /reset`, and `POST /response` retain their current machine-facing behavior.
- Existing `/drop`, `/redirect`, `/oversized`, and query-driven status/delay behavior remains intact.

The page may poll or refresh locally so a newly delivered Note appears without restarting the browser. Displayed metadata is HTML-escaped. Audio URLs are derived from server-assigned validated Attempt IDs rather than untrusted filenames.

## Data and Lifecycle

Each accepted Attempt is held in an in-memory record. The audio bytes are stored directly rather than recovered from the base64 representation of the complete multipart body. The existing `/state` response remains compatible with current tests; browser-only fields do not change the webhook contract.

The first Attempt for a Note has `duplicate: false`; later Attempts carrying the same Note ID have `duplicate: true`. Each Attempt remains separately visible and playable. `POST /reset` removes both the visible records and all retained audio bytes, and resets response simulation to its defaults. Stopping the process discards everything.

## Error Handling and Safety

Invalid multipart requests continue returning `400` and do not appear in the browser. Missing audio records return `404`. The inspection UI does not render request headers or secrets. The tool listens on loopback by default and makes no external requests. Opting into LAN access exposes its inbox, audio, and control routes to reachable devices; use a trusted development network.

## Verification

Add Node tests at the public HTTP seam by spawning the fixture on an ephemeral port. Tests will prove that:

1. the empty browser page renders successfully;
2. a valid Whim multipart request appears in the list with escaped metadata;
3. its audio endpoint returns the exact submitted bytes and `audio/mp4` media type;
4. duplicate Attempts remain separately visible with the correct duplicate state;
5. reset removes both the listing and audio access; and
6. existing machine-facing fixture behavior remains compatible.

The Node tests remain part of the root unit suite. Before completion, run the affected tests, then `npm run test:all` as required by repository policy.


## Running on the local network

```sh
WHIM_WEBHOOK_HOST=0.0.0.0 npm run test-server
```

From another device on the same network, open `http://<Mac-LAN-IP>:8787/`.
The inbox shows the Mac's detected IPv4 address; use the address for the shared
network if the Mac has multiple interfaces. `0.0.0.0` is a bind address, not the
address to enter on the other device. Override the port with `WHIM_WEBHOOK_PORT`.

Whim requires HTTPS for its webhook URL. For app delivery, also set
`WHIM_TLS_KEY_PATH` and `WHIM_TLS_CERT_PATH` to a key and certificate valid for
the hostname or IP used by the device, with a certificate chain the device
trusts. Then use `https://<Mac-LAN-IP>:8787/receive` (or the certificate's hostname)
as the webhook URL and `https://<Mac-LAN-IP>:8787/` for the inbox.

Manual acceptance: with the Mac and iPhone on the same network and the server
running with TLS, open the inbox from the phone, configure the HTTPS webhook,
and run Whim's configuration test. Confirm the received Attempt appears and
its audio plays. This verifies device trust and local firewall/network access
that a loopback automated test cannot prove.
